## 3. 应补使用前提或拆开决策的项

### #7012：第一档需要 EasyPay 使用前提

原 note 已承认 value-gated，但排序没有区分“代码有缺陷”和“本部署会受影响”。
`backend/internal/service/payment_config_providers.go` 中的正则只有配置 EasyPay 自定义 upstreamType 时才产生收益。
启用 EasyPay 且需要带点号的上游标识时，保留第一档合理；未使用时应按第三档按需处理。
同理，支付/订阅/兑换界面项应注明是否为当前部署路径，不能只对新平台应用“按需”原则。
本次没有读取生产配置，因此不直接断言该项必须降档。

### #6654：注册确认密码是增强，不是已成立的兼容性修复

来源在 `frontend/src/views/auth/RegisterView.vue` 新增确认输入框和校验（46行产品新增）。
当前归第二档并非技术错误，但对单机/关闭注册的部署缺少价值依据。
建议第三档，或在公开注册且明确需要此体验时保留第二档；不要排在兑换结果、导出数据和桥接正文修复之前。

### #7064 与 #7043：正确执行配置，不等于必须扩大默认资源预算

`backend/internal/service/openai_ws_pool.go:1882` 的 v2 提前返回绕过 factor，#7064 修复此错误，第二档合理。
`backend/internal/config/config.go:2426` 当前默认 factor=1.0；#7043 把 OAuth/API Key 两者改成5.0，属于容量策略。
第二档可以保留其评估，但“pair with 7064”不能解释成修复必须同时采用5.0：

- 先使用户已配置的 factor 在 v2 下生效，保留 hard cap 和无限并发分支语义。
- 再按 ctx_pool 活跃会话、账号并发、内存/FD余量及现有配置覆盖情况决定是否提高默认值。
- 5.0 是池上限系数变化，不代表实际连接数或请求并发必然增加五倍；也不能当作无资源代价的纯 bugfix。

本仓库文档面向小型单机，这个区分尤其有意义；未测负载前不建议机械采用上游默认值。
