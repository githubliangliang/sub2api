## S08 independent implementation review

Reviewed the three existing service entry points (`Forward`, `ForwardNative`, `ForwardAsChatCompletions`), their stream readers, the shared client writer and image counter, and all three handler-to-usage-queue paths against the S08 spec. Production changes remain owned by the root agent.

Confirmed in the current service implementation:

- A standalone upstream `context.Canceled` with a live request context remains an error. The partial-success read-error branch also requires the request context to confirm that the client has gone and requires actual observed tokens or images.
- The shared writer remembers its first write/short-write error, prevents later underlying writes and flushes, and checks request cancellation. Write failure before observing any tokens or images returns an error and nil result; no model-name image fallback makes that attempt billable.
- Non-EOF read errors are checked before parsing residual bytes, so even valid JSON returned with such an error is not accepted as another observed SSE frame. Existing normal final-line-at-EOF handling is retained.
- Interrupted requests count actual inline image parts with image MIME plus nonempty data, or fileData/file_data image references with a nonempty URI. A finishReason or image-model name alone does not add an image. The interrupted counter uses the existing per-payload maximum to avoid charging repeated cumulative frames; separate incremental image chunks can still be conservatively undercounted, as in the existing counter policy. Complete requests retain their prior fallback path. No file URI is downloaded by this observation.
- Each stream result records `clientDisconnect` and whether it received a finishReason. All three public forwarders place ClientDisconnect on ForwardResult and log `stream_finished` on disconnect; no new persistence schema is introduced. Every forwarding attempt resets image observation, so failover attempts do not inherit earlier image counts.
- S07 policy decisions are reset per retry response and reused only for that same response. Its credential-build errors and HTTP error policy run before the S08 stream readers. The shared-capacity and quota-details classifier, exact service-account-not-found classification and transient/cancellation safeguards remain separate from client-disconnect success.

Found and reported a concrete handler integration gap: Messages' Gemini result path and the native Gemini handler still used `submitUsageRecordTask`, whose configured drop/sample overflow modes can discard billing tasks. Their queued closures also called `clientRequestedUsageFields(c, ...)` after the handler returned, unlike the Chat path's pre-captured fields. A reused Gin context could therefore change metadata or race with the worker. Existing SQLite abort tests used an available sync-policy queue and no channel metadata, so they did not prove these boundaries.

The root agent confirmed this gap and assigned failing SQLite queue-saturation and metadata-reuse regressions before changing those two paths to mandatory submission plus field snapshots. `s08-queue-before` reproduces four failures (Messages/native each lose saturated-queue usage and capture next-request metadata; Chat is the passing control). The root agent's changes now capture `channelUsageFields` before submission and use `submitMandatoryUsageRecordTask`; the worker closures no longer read Gin for these fields. Independent source review confirmed both connections. `s08-queue-after` and `s08-queue-race` pass, and `backend-unit-accepted` passes all 54 backend unit packages on the final production implementation. No additional blocking defect was found in the service-side S08 or adjacent S07 review described above. This is local fixture/source evidence, not verification with real Gemini/Vertex credentials or provider model permissions.

## Whole-suite fixture determinism

Two existing service tests failed in intermediate full runs; neither production implementation was changed for these failures.

The Antigravity Gemini keepalive fixture closed its upstream after a fixed 1.2 seconds. The ticker starts before the first data updates `lastDataAt`; its first tick can therefore fall just short of a full idle interval and be skipped, making the next eligible tick about 2 seconds after startup. `audit-keepalive-before` repeats the original test 12 times and reproduces one failure. The fixture now keeps the upstream open until the ordinary client actually observes a keepalive, bounded by a five-second failure deadline, and joins the stream after closing. The comment-intolerant-client control remains a negative assertion, held open through two ticker opportunities. The production timing and both output assertions are unchanged.

The tool-schema allocation guard uses `testing.AllocsPerRun`, which reads process-wide `runtime.MemStats.Mallocs` even while it temporarily sets GOMAXPROCS to 1. Background workers in the same service test process can be counted during the large-body window; unrelated Go processes cannot directly add to that counter, although CPU contention can change scheduling/GC timing. The intermediate full-run observation was small 7 / large 76; 30 isolated repetitions (`audit-alloc-isolated-before`) all pass. The final fixture runs the exact original two-sample allocation comparison, 4 versus 2000 hits and unchanged `small+40` bound, in a fresh instance of the same test executable. It does not add retries, alter GC settings, increase the threshold or skip the guard.

`audit-fixture-after` passes 8 repetitions of both keepalive cases and the isolated guard; measured production allocations are small 7 / large 17. `audit-fixture-race` passes 3 repetitions with race instrumentation, with the same counts. `audit-alloc-linear-negative-control` uses a temporary Go overlay to replace the one-pass rewrite with a full-document copy per hit: the unchanged guard fails inside the child with small 10 / large 2016. This verifies that subprocess isolation still detects the intended linear-allocation regression. This overlay is only a mutation control, not an unmodified historical baseline. The final test-only edits are in `gemini_sse_comment_compat_test.go` and `openai_responses_tool_schema_test.go`; the root agent accepts the final-production full unit pass plus these final-fixture targeted/race results as the closure.
