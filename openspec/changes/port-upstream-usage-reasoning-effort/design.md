# 设计

## 采集时机与含义

请求值取自客户端进入网关时的原始请求，在分组映射、上限、模型替换及桥接默认值注入之前捕获。按已有协议读取 `reasoning.effort`、`reasoning_effort` 或 `output_config.effort`。同一请求有多个显式表示时依此顺序取第一个非空值。显式值缺省才使用客户端原始模型名的已知 effort 后缀；显式未知值记为未取得。按本地已支持的取值规范化大小写及已知拼写，保留有意义的 `none` 与 `max`。网关推导的默认 medium 和账号映射目标的后缀都不是客户端声明。

实际值取自完成策略和模型族转换后、用于本次成功转发的值；它描述网关发出的请求。继续沿用已有协议的拒绝、默认及用量生成逻辑。普通 HTTP 与 SSE 的用量属于同一请求；WS 在每个 create 帧开始时单独取得请求值，再将两份值复制进该轮的用量工作项。重试保留初始请求值，选中新账号后的成功结果提供实际值。

## SQLite 与兼容

新增 `usage_logs.requested_reasoning_effort TEXT NULL`。`reasoning_effort` 继续保存已有的实际值。基线最大迁移号为 229，实施时取下一个可用编号。单条、批量、best-effort、列表与详情须使用同一列顺序和可空类型。旧行保持 NULL，无需推测当时的请求。该列是诊断数据，不能进入结算去重指纹或触发历史重算。

来源 PR 有在写入时用实际值回填请求值的分支。本地选择把回退放到 DTO 展示层，从而能区分客户端明确请求 medium 与兼容桥合成 medium。已有单值行仍能显示。使用真实 SQLite 从 229 升级并回读新旧行，覆盖相同 request ID 重复提交和固定 quota。

## API、界面与导出

普通用户的 `reasoning_effort` 优先返回请求值，缺省才沿用原来的实际值。管理员继承同一主字段，并在两值已知且规范化后不同时获得 `upstream_reasoning_effort`。管理员表格显示两者关系，导出能辨认两列；普通用户列表、详情及导出仅使用用户 DTO。两值相同或只有历史单值时，界面只显示一项。详情和导出不得将缺失值渲染成一次实际发生的改写。
