# Proposal

## Why

SQLite 部署仍在 DI 层跳过三个既有后台服务，造成待执行清理任务无法周期续跑、到期自动暂停不执行、已配置定时测试不执行。操作日志的全量清理使用 SQLite 不支持的 TRUNCATE，管理员通过 TOTP 校验后仍得到数据库语法错误。网关还在正常请求中提前识别单 Antigravity 账号，模型映射校验为每次读取分配、排序临时键列表。

## What Changes

- 按数据库操作逐项验证三个后台服务，恢复已有启动与配置语义，保证停止后不继续工作。
- 修复审计日志全量清空的 SQLite SQL，保留管理员会话、现场 TOTP、机器凭证拒绝与同步清理留痕。
- 移植 #8249 的请求内延迟探测与 #8250 的零分配签名，并测量分配量和耗时。
- 对新启用的任务路径验证旧 TEXT 时间列、不同时间格式、失败/取消/续跑、筛选范围和调度快照传播。

## Impact

后台服务、相关 raw SQL 仓储、网关请求元数据与账号映射；操作日志页面保持现有交互。测试使用临时 SQLite、本地 HTTP 夹具和 miniredis，不访问业务实例。现有配置开关及计划启用状态继续决定任务是否执行。

不添加 schema、迁移、支付、新平台或全局快照缓存。发布、push、tag、部署及实际清空业务日志不属于本次实施。
